How a PDF gets onto this phone
Six steps, and the order of them is the argument. A file that finished downloading is not the same fact as a document that opens, so the move into place happens after the checks and never before.
The path the bytes take
Authorised first
library.downloadUrl is a mutation, not a query — a cached URL outliving its signature is a download that fails for no visible reason. Ownership is checked before a URL exists.
Into a temp name
<id>.download, beside where it is going. A half-arrived file must never sit under the name the scan reads as “this is here”.
Checked three ways
The size the account recorded. The first five bytes reading %PDF-. The file’s hash — the whole thing under 32 MB, head and tail above it.
Moved, atomically
One rename. There is no moment at which a partial file is visible under the real name, on any platform.
Recorded locally
documentFiles goes to available with the verified hash and the moment it was checked. This row is the only truth about offline availability.
And that is the end
Nothing is sent. Opening it afterwards touches no network, resolves no URL and waits on no subscription.
Never
A path on the wire
/data/user/0/… means something on exactly one device. It is never an argument, never a column, never a log line.
A field saying “downloaded”
The account has no idea which devices hold which files, and should not. It would be a stale flag on the one screen whose job is to answer that.
A URL that outlives its use
Five minutes, signed, minted after the ownership check. A paused download stores one only inside the encrypted database, and clears it the moment the transfer settles.
The filename is the document id, and that is a security control rather than a convention. A PDF the reader imported as ../../../shared_prefs/auth.xml is a title and nothing else — traversal is closed by construction rather than by sanitising a hostile string and hoping the sanitiser is complete.
